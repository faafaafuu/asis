# Техническое задание — AI Selection Popup («Суфлёр»)

Версия 1.0 · на основе дизайн-референса `AI Popup.dc.html` и хэндовер-документа `README.md`

## 1. Назначение и общая идея

Системный (a не встроенный в конкретный сайт/приложение) инструмент: пользователь выделяет
любой текст в любом приложении на устройстве, и рядом с выделением всплывает окно с
AI-объяснением этого текста. Окно можно раскрыть («?») для упрощённого объяснения и примеров,
а также «доспросить» в свободной форме — с учётом исходного термина как контекста.

Ключевое отличие от браузерного расширения или веб-виджета: попап должен появляться **поверх
любого приложения ОС**, а не только внутри одной веб-страницы. Это определяет архитектуру —
нужен нативный доступ к системному выделению текста и оверлей-окно без рамки, стоящее поверх
всех окон.

## 2. Платформы и стек

- **Desktop (Windows / macOS / Linux)** — Tauri 2 + Rust. Frontend попапа — тонкий HTML/CSS/JS
  слой во встроенном webview Tauri, идентичный дизайн-референсу. Системная интеграция
  (получение текста выделения, глобальный хук на Ctrl+выделение, оверлей-окно без декораций,
  always-on-top, позиционирование по экранным координатам) — на стороне Rust/нативных API ОС.
- **Mobile (Android / iOS)** — тот же Tauri-проект в режиме `tauri android` / `tauri ios`,
  тот же frontend-компонент попапа. Точка входа другая: не глобальный хук, а нативный пункт
  меню в системном контекстном меню выделения (см. §7).

## 3. Триггер открытия

### Desktop
- Открытие происходит на `mouseup`, если выделение непустое **и** во время выделения был
  зажат **именно левый** `Ctrl` (`ControlLeft`, не правый `ControlRight`).
- Проверка текста выделения — с задержкой в один тик (`setTimeout(…, 0)`), чтобы Selection API
  успел зафиксировать финальное состояние после `mouseup`.
- Клик по кнопке/интерактивному элементу или клик внутри уже открытого попапа/меню не должен
  триггерить повторное открытие.
- Обычное выделение без Ctrl **не** открывает окно — это обязательное отличие от предыдущей
  версии ТЗ, чтобы не мешать штатному copy/paste и работе с текстовыми полями.

### Mobile
- Глобальный перехват выделения мышью недоступен на уровне ОС для сторонних приложений.
- Вместо этого при выделении текста в системное контекстное меню (или наше overlay-меню-имитация,
  если ОС это позволяет) добавляется пункт **«Объяснить»** рядом с «Копировать».
- Тап по пункту открывает тот же попап-компонент, что и на десктопе, с тем же набором состояний.

## 4. Позиционирование окна (десктоп)

- Точка привязки — **последний** прямоугольник выделения (`Range.getClientRects()`, последний
  rect в списке, а не bounding box — важно для многострочных выделений, где нужно поставить
  окно у конца выделенного текста, а не у его геометрического центра).
- Окно ставится **над** выделением, отступ 12px, по горизонтали центрируется на выделении.
- Если сверху не помещается (`top < 12px` от края экрана) — окно отзеркаливается **под**
  выделение (`bottom + 12px`).
- Экранный inset — 12px по всем краям. Если окно всё равно не влезает по вертикали — прижимается
  к нижнему краю минус inset.
- Ширина: 400px в обычном состоянии, 480px в раскрытом; при нехватке места по горизонтали —
  `100vw − 24px`.
- Перед первым позиционированием окно замеряется скрытым (`visibility: hidden`), чтобы избежать
  видимого «прыжка» при появлении.
- При скролле документа/содержимого под выделением окно **не закрывается**, а пересчитывает
  позицию вслед за выделением через `requestAnimationFrame`, пока выделение остаётся в пределах
  вьюпорта (+40px запас); при выходе за пределы — закрывается.
- Появление: `opacity 0→1`, `translateY(4px)→0`, 130ms ease-out.

На десктопе в терминах Tauri это означает: окно попапа — отдельное `WebviewWindow` без рамки
(`decorations: false`), `always_on_top: true`, `skip_taskbar: true`, прозрачный фон
(`transparent: true`), позиция и размер выставляются императивно из Rust на основе экранных
координат, которые фронтенд получает через системный хук выделения (см. §6), а не через
браузерный `Range` API (он недоступен вне контекста самого приложения, у которого произошло
выделение).

## 5. Внешний вид

Форма: прямоугольник, `border-radius: 10px`.

Фон — Acrylic/Mica-подобный эффект:
| Тема | Фон | Фолбэк без blur |
|---|---|---|
| Dark | `rgba(27,24,21,.87)` + `backdrop-filter: blur(22px) saturate(150%)` | `#1B1815` |
| Light | `rgba(253,251,246,.90)`, тот же blur | `#FDFBF6` |

- Граница 1px: `rgba(255,240,220,.10)` (dark) / `rgba(60,45,25,.09)` (light).
- Тень: `0 1px 2px rgba(0,0,0,.30), 0 16px 44px -10px rgba(28,20,10,.60)`
  (light: последний слой `rgba(40,30,15,.32)`).
- Padding: 14px.
- Текст: `#F2ECE1` (dark) / `#221F1B` (light), контраст ≥ 7:1 к сплошному фолбэку.
- Акцент: `oklch(.86 .09 68)` (dark) / `oklch(.48 .11 48)` (light).
- Ошибка: `#E2705F` (dark) / `#C2503C` (light).

### Типографика
- UI-текст: IBM Plex Sans → Segoe UI → system-ui, 14px / line-height 1.4.
- Выделенный термин (в шапке): IBM Plex → **Instrument Serif italic**, 19px / 1.15,
  цвет акцента, одна строка с ellipsis.
- Служебные подписи: IBM Plex Mono, 10–12px, uppercase, letter-spacing 0.12em.

Полная таблица токенов дизайна — в README (раздел «Design tokens»), она воспроизводится
как есть без интерпретации.

## 6. Состояния попапа

1. **Loading** — появляется мгновенно, не дожидаясь ответа сети. Спиннер 12px
   (`border 1.5px`, `border-top` акцентный, `spin 0.7s linear infinite`) + текст «Анализирую…».
   Ниже — скелетон из 3 полос высотой 9px (100% / 88% / 54%), пульсация `1.2s ease-in-out`
   со сдвигом 0 / 0.15s / 0.3s.
2. **Success** — короткое определение термина по сути, без служебных фраз вроде «фрагмент из
   абзаца». Тело: `max-height: 340px`, `overflow-y: auto`, тонкий скроллбар.
3. **Error** — одна строка: точка-индикатор 6px цвета ошибки + текст (по умолчанию
   «Сбой сети — нет ответа», настраиваемый).

## 7. Раскрытие («?») и доспросить

- Клик по «?» в шапке (без потери фокуса документа — `preventDefault` на `mousedown`):
  окно расширяется 400px → 480px, добавляются блоки «Простыми словами» и «Примеры»
  (2–3 пункта, маркер «·»). Кнопка исчезает, вместо неё — точка-маркер в шапке.
- Follow-up тред — только в раскрытом состоянии, под примерами, с разделителем сверху:
  вопрос курсивом (Instrument Serif italic, 15px, акцент), ответ обычным текстом (13.5px).
  Пока ждём ответ — строка «Думаю…» со спиннером 10px. Поле ввода «Спросить ещё…» получает
  фокус только по явному клику пользователя; `Enter` = отправить. Запрос идёт через тот же
  AI-клиент, с исходным термином как контекстом.

## 8. Жизненный цикл и фокус

- Фокус клавиатуры не перехватывается: контейнер не ловит фокус сам по себе, `mousedown`
  внутри окна не даёт странице терять текущее выделение/фокус (кроме явного клика в поле
  ввода «доспросить»).
- Закрытие: `Esc` (глобальный listener на capture-фазе), клик вне окна, потеря выделения текста,
  выход выделения за пределы вьюпорта при скролле.
- Повторное выделение при открытом окне — переоткрытие с новым якорем и сбросом состояния,
  без анимации закрытия.
- Все таймауты/отложенные запросы отменяются при закрытии/размонтировании компонента.
- Окно рендерится в отдельном слое поверх всего остального контента, не наследует
  transform/overflow родительских контейнеров (на десктопе это в принципе гарантировано тем,
  что это отдельное системное окно, а не DOM-узел внутри чужой страницы).

## 9. Системная интеграция по платформам

### 9.1 Windows
- Получение текста и координат выделения — через **UI Automation** (`IUIAutomation`,
  `GetFocusedElement` → `TextPattern`/`TextPattern2`, `GetSelection()` → `BoundingRectangles`).
- Глобальный хук на левую кнопку мыши и состояние `Ctrl` — низкоуровневый хук
  `WH_MOUSE_LL`/`WH_KEYBOARD_LL` либо polling через `GetAsyncKeyState(VK_LCONTROL)`.
- Оверлей-окно — слоистое окно (`WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_TOPMOST`),
  без рамки, с поддержкой per-pixel alpha для blur/acrylic (либо DWM `SetWindowCompositionAttribute`
  для настоящего acrylic-эффекта, либо фолбэк на сплошной фон).
- Известное ограничение: UI Automation не одинаково полно реализован во всех приложениях
  (особенно кастомные рендереры вроде Electron без корректной поддержки a11y-дерева) —
  для таких приложений нужен фолбэк на буфер обмена (симулировать `Ctrl+C` и читать clipboard),
  что менее надёжно и требует явного пользовательского согласия в настройках.

### 9.2 macOS
- Получение текста выделения — через **Accessibility API** (`AXUIElement`,
  `AXSelectedText`, `AXSelectedTextRange`, `AXBoundsForRange` для координат).
- Требует явного разрешения пользователя: **System Settings → Privacy & Security →
  Accessibility** для приложения. Без этого разрешения функциональность недоступна —
  приложение должно детектировать отсутствие разрешения и показывать понятный onboarding.
- Хук на `Ctrl`-модификатор при выделении — через `NSEvent.addGlobalMonitorForEvents`
  (`.leftMouseUp`, проверка `event.modifierFlags.contains(.control)`), для точного различения
  левого/правого `Ctrl` нужен разбор `keyCode` при последнем `flagsChanged`-событии
  (левый = 59, правый = 62 на стандартной раскладке — уточняется через `CGEventGetIntegerValueField`).
- Оверлей-окно — `NSPanel` с `.nonactivatingPanel`, `.borderless`, `level: .floating`,
  `NSVisualEffectView` для acrylic/vibrancy.

### 9.3 Linux
- Портируемого системного способа получить текст выделения из произвольного приложения
  на уровне ОС не существует так же надёжно, как на Windows/macOS.
- X11: частично решаемо через `AT-SPI2` (`atspi` D-Bus интерфейс) для accessible-приложений,
  либо через чтение X11 **PRIMARY selection** (`xclip -selection primary -o` / `x11rb`) —
  последнее ловит любое mouse-выделение, но не даёт координат/bounding rect напрямую
  (только текст), поэтому окно придётся позиционировать относительно текущей позиции курсора,
  а не относительно самого выделения.
- Wayland: ещё более ограничено по соображениям безопасности протокола — глобальные хуки
  клавиатуры/мыши и чтение PRIMARY selection в общем случае недоступны без компоузитор-специфичных
  расширений (`wlr-layer-shell`, `zwp_input_method`) или запуска с повышенными привилегиями.
  Реалистичный MVP на Wayland — poll PRIMARY selection через `wl-clipboard`/`wl-paste -p`
  с позиционированием у курсора, без полноценного глобального хука на Ctrl.
- Это осознанное и документированное ограничение: Linux-поддержка в MVP — best-effort,
  с понятным сообщением пользователю, если системная интеграция недоступна на его окружении.

### 9.4 Android
- Основной механизм — **`ACTION_PROCESS_TEXT`** intent-filter: система сама добавляет
  зарегистрированный intent-filter как пункт в контекстное меню выделения текста в любом
  приложении, поддерживающем `android:process_text` (это подавляющее большинство современных
  текстовых полей и WebView). Пункт меню называется «Объяснить», активность-обработчик получает
  выделенный текст через `Intent.getCharSequenceExtra(Intent.EXTRA_PROCESS_TEXT)` и открывает
  попап-компонент как floating-activity/overlay поверх вызывающего приложения.
- Альтернатива/дополнение — `AccessibilityService` для более тонкого позиционирования окна
  относительно реальных координат выделения (`AccessibilityNodeInfo.getTextSelection*`),
  но это более тяжёлый путь с отдельным разрешением и не обязателен для MVP.
- Реализуется как нативный Tauri-плагин на Kotlin (см. `mobile/android-plugin/`).

### 9.5 iOS
- Кастомизация системного меню выделения текста — через **`UIEditMenuInteraction`**
  (iOS 16+, современный API) или legacy **`UIMenuController`** (для более старых версий) —
  добавление своего пункта «Объяснить» в меню, которое система показывает при выделении текста
  внутри `UITextView`/`WKWebView` **нашего же приложения**.
- Важное ограничение iOS: полноценно перехватить/дополнить меню выделения текста в **чужих**
  приложениях (Safari, Notes и т.д.) с уровня стороннего приложения не даёт ни один публичный
  API. Реалистичный сценарий на iOS — Share Extension («Поделиться» → «Объяснить») либо
  собственный in-app браузер/reader-режим, где мы полностью контролируем текстовый контент.
  Это отличается от README (там сказано мягче — «показывайте меню-имитацию, если ОС позволяет»),
  и в разделе рисков (§12) это обозначено явно.
- Реализуется как нативный Tauri-плагин на Swift (см. `mobile/ios-plugin/`).

## 10. AI-клиент

- Единая абстракция на фронтенде (`ai-client.js`) и на бэкенде (`ai_client.rs` trait
  `AiProvider`), не завязанная на конкретного провайдера.
- Методы: `explain(term, contextText) → { def, simple, examples[] }`,
  `ask(term, contextText, thread, question) → answer`.
- В комплекте — `MockProvider` (детерминированные ответы для разработки и демо-режима,
  повторяющего кнопки «Загрузка/Ответ/Ошибка» из референса) и заготовка `HttpProvider`
  для реального API (ключ и endpoint — из конфигурации приложения, не хардкодятся).
- Таймауты и retry-политика конфигурируются, ошибка сети маппится в состояние `Error`
  с текстом по умолчанию «Сбой сети — нет ответа».

## 12. Риски и осознанные ограничения (важно прочитать перед оценкой сроков)

1. **Linux** не даёт единого надёжного системного API для глобального выделения — поддержка
   в MVP ограничена (см. §9.3), это не баг, а свойство платформы.
2. **iOS** не позволяет дополнять системное меню выделения в чужих приложениях — README
   описывает это оптимистичнее, чем позволяют публичные API; реалистичный охват — собственный
   контент приложения + Share Extension (см. §9.5).
3. **Windows UI Automation** не одинаково полно реализован в приложениях с кастомным рендерингом
   (часть Electron/кастомных UI-тулкитов) — для них нужен clipboard-фолбэк с понятным UX
   («не удалось определить выделение напрямую — использовать буфer обмена?»).
4. **macOS Accessibility permission** — без явного разрешения пользователя приложение не
   получит вообще ничего; это должно быть явным шагом onboarding при первом запуске.
5. Точное различение **левого и правого Ctrl** — не на всех платформах тривиально
   (особенно с нестандартными раскладками/маппингом клавиш) — фолбэк-поведение должно быть
   безопасным (не открывать попап, а не открывать его при любом Ctrl).
6. Blur/acrylic-эффект (`backdrop-filter`) в системных наложенных окнах десктопных тулкитов
   не всегда идентичен браузерному — на Windows/Linux вероятен визуальный фолбэк на сплошной
   фон вместо честного blur, это допустимо и предусмотрено в самом дизайне (см. §5, «фолбэк»).

## 13. Вне рамок MVP

- Синхронизация истории объяснений между устройствами.
- Персонализация/память между сессиями (кроме текущего треда «доспросить» внутри одного
  открытого попапа).
- Поддержка нескольких языков UI (сейчас — только русский интерфейс, как в референсе).
- Аналитика использования.

## 14. Критерии приёмки MVP (десктоп)

- Ctrl (именно левый) + выделение текста в любом стороннем приложении на macOS и Windows
  открывает попап рядом с последним rect выделения не более чем за 1 кадр визуальной задержки
  (окно уже видимо, состояние `Loading` показано мгновенно).
- Обычное выделение без Ctrl не открывает попап ни в одном сценарии.
- Все состояния (`Loading`/`Success`/`Error`), раскрытие и follow-up-тред визуально и по
  таймингам соответствуют дизайн-референсу `AI Popup.dc.html`.
- Esc, клик вне окна, потеря/выход выделения за пределы экрана закрывают попап.
- При отсутствии разрешения Accessibility (macOS) — понятный экран с инструкцией, а не тихий
  отказ без обратной связи.
