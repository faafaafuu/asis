# Промпт для агента: сборка «Суфлёра» по ТЗ

Скопируй всё, что ниже, в Claude Code (или другой агентный кодинг-инструмент) в директории
проекта, рядом с `SPEC.md` и дизайн-референсом `AI Popup.dc.html`.

---

Ты реализуешь проект целиком по прикреплённому `SPEC.md` — это финальное ТЗ, не черновик.
Дизайн-референс `AI Popup.dc.html` — источник истины по вёрстке/анимациям/таймингам,
воспроизводить как есть, без отсебятины. Не проси меня уточнять то, что уже написано в
`SPEC.md` — прочитай его целиком перед стартом.

## Стек и охват

- Tauri 2 + Rust. Desktop (Windows/macOS/Linux) — полноценно. Mobile (Android/iOS) —
  тоже часть охвата, включая нативные плагины (Kotlin/Swift), а не только заглушки.
- Frontend попапа — тонкий HTML/CSS/JS во встроенном webview, без тяжёлых фреймворков
  (React не нужен — компонент простой, вёрстка фиксированная по дизайн-токенам).
- Все дизайн-токены (цвета, радиусы, тайминги, шрифты) — только из `SPEC.md` §5, §11
  и `AI Popup.dc.html`. Не придумывай свои значения.

## Порядок работы (обязателен)

1. Прочитай `SPEC.md` целиком и `AI Popup.dc.html`, выпиши себе чек-лист состояний/переходов
   попапа (Loading/Success/Error, раскрытие, follow-up-тред, меню на мобильных).
2. Инициализируй git-репозиторий (если ещё не инициализирован).
3. Веди разработку **фазами**, коммить после каждой законченной фазы — не одним коммитом в
   конце и не микрокоммитами на каждый файл. Ориентировочные фазы:

| # | Фаза | Что входит |
|---|---|---|
| 1 | Каркас проекта | структура папок, `Cargo.toml`, `package.json`, `tauri.conf.json`, `.gitignore` |
| 2 | Frontend попапа | HTML/CSS/JS попапа, все состояния и анимации, тёмная/светлая тема |
| 3 | Мобильное мини-меню | компактная плашка «Копировать / Объяснить» |
| 4 | AI-клиент | абстракция провайдера + мок-реализация, реальный HTTP-провайдер как заготовка |
| 5 | Rust-ядро Tauri | команды, состояние, оверлей-окно, позиционирование по SPEC §4 |
| 6 | Windows-интеграция | UI Automation, хук на левый Ctrl, известные ограничения (SPEC §9.1) |
| 7 | macOS-интеграция | Accessibility API, permission-онбординг, хук на левый Ctrl (SPEC §9.2) |
| 8 | Linux-интеграция | best-effort по SPEC §9.3, с честным сообщением при недоступности |
| 9 | Android-плагин | `ACTION_PROCESS_TEXT`, пункт «Объяснить» (SPEC §9.4) |
| 10 | iOS-плагин | `UIEditMenuInteraction`, ограничения по чужим приложениям (SPEC §9.5) |
| 11 | Полировка | обработка ошибок/таймаутов, доступность, README с инструкциями сборки |

Порядок можно менять, если так логичнее по зависимостям, но каждая фаза = отдельный(е)
коммит(ы) по завершении, не раньше.

## Требования к коммитам

- Сообщения — **на русском, человеческим языком**: что сделано и зачем, а не `fix`, `wip`,
  `update stuff`. Пример хорошего сообщения: «Добавить позиционирование попапа над/под
  выделением с учётом screen inset и пересчётом при скролле».
- Один коммит = одна логически завершённая часть, которая не ломает сборку остального.
- Если часть фазы реализована как заглушка/TODO (например, нет возможности протестировать
  на реальном устройстве) — это должно быть явно написано в теле коммита и в коде
  (`// TODO:` с объяснением, чего не хватает: устройства, разрешения ОС, тулчейна).

## Честность по ограничениям (важно)

В `SPEC.md` §12 перечислены осознанные ограничения платформ (Linux без единого API,
iOS не даёт трогать чужие приложения, Windows UI Automation неполный в части приложений,
macOS требует ручного разрешения Accessibility). Не скрывай эти ограничения и не делай вид,
что они решены, если реально сделан только фолбэк или заглушка. Если для какой-то части
нужен реальный девайс/Xcode/Android Studio, которых нет в текущем окружении — так и пиши
в коммите и в README, а не оставляй мёртвый код без объяснения.

## Критерии готовности

Перед тем как считать задачу выполненной, сверься с `SPEC.md` §14 (критерии приёмки MVP)
и явно ответь по каждому пункту: выполнено / выполнено частично (с чем) / не выполнено
(с чем и почему).
